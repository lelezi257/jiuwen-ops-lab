02

具体案例：订单优惠码回归

先把一个可解释、可重现的代码故障做真。应用框架建议 Python HTTP 服务，数据库采用 PostgreSQL；仓库 URL 尚待选择。

业务路径正常版本 A故障版本 B修复候选 C
购买 2 件 × 100 元，不填优惠码200 元，成功持久化订单HTTP 500，订单未创建200 元，成功持久化订单
购买相同商品，使用有效九折码180 元，成功持久化订单仍正常，便于识别局部回归180 元，成功持久化订单
读取刚创建订单金额、商品、数量正确已有订单仍可读新旧订单均可读
无效输入 / 无效优惠码按固定业务合同拒绝不作为本例主故障错误语义保持，无乱放行

故障由谁制造

实验准备阶段先部署正常版 A，采集基线，再通过单独的实验入口部署包含优惠码空值处理缺陷的 B。故障注入器属于实验装置，不属于 Agent，且不向 Agent 提供故障标签、正确文件行号或修复补丁。

为什么坏版本可以上线，而后面的 CI 又能阻止同类问题？

坏版本代表一个历史测试遗漏：原有普通测试覆盖有效优惠码，漏了不填优惠码的路径。独立验收方保留完整业务合同；故障后候选 C 必须通过该合同，并由 Agent 增加回归测试。两种测试职责明确，不能一边声称坏版通过完整合同，一边又声称合同能发现它。

真实程度的边界

商品与订单是测试数据，不接支付网关。应用、数据库、请求失败、模型推理、文件修改、GitHub PR/CI、镜像部署和恢复探测都要求真实。代码需进入我们有管理权限的演示仓库；若选现成项目，先适配同一业务合同，不向原项目自动提交变更。

04

大组件部署关系

同一 VM 内是多个独立服务。Swarm 与 Core 位于九问执行单元内部，并不各自变成一个远程服务。

部署单元进程 / 容器建议持久化与权限首版边界
运维控制中心ops-control：自己的 Web/API + 调度器独立 SQLite 卷、事件/任务/授权账本任务并发 1；重启后先对账再推进
九问执行服务jiuwen-runner 常驻父进程；每次 run 创建 CLI 子进程独立 Swarm 数据目录、报告工作区；仅模型 Key 和工具服务身份不挂 Docker socket，不持有合并/发布凭证
取证服务ops-evidence 独立容器查询 Prometheus/Loki；读受控发布与源码视图只读、限服务/时窗、分页与证据留存
工程交付服务ops-delivery 独立服务；按任务创建测试容器工作区与发布账本；服务端保管 GitHub/镜像/部署凭证Agent 令牌只能编辑/测试/提 PR；控制身份才可合并/发布
观测组Prometheus、Alertmanager、Loki、日志采集器，各自独立监控/告警配置和数据卷；采集器权限独立于 Agent应用导出真实指标；日志采集后供取证查询
业务组order-api、PostgreSQL，两个独立容器应用版本配置；数据库独立数据卷不在首版做数据库结构变更

外部依赖GitHub repo + Actions / 制品，真实模型 API身份在相应服务中配置；VM 平台架构与镜像匹配仓库、模型、VM 资源尚待选择

网络与启动顺序

Mac 仅访问转发的工作台入口和可选业务演示入口。服务间走 VM 容器网络。数据库只供业务应用使用；取证服务通过受限数据核验接口检查订单，不给模型数据库管理员权限。先启动数据库、应用和观测，再启动工具/交付服务、九问执行服务与控制中心；健康状态都满足后才允许启动实验。

资源预算是建议，不是已确认环境

初步按 4–6 vCPU、8–12 GiB 内存、60 GiB 磁盘评估；模型推理在外部。实际应根据 Mac 可用资源和组件实测调整。Mac / VM 若为 arm64，CI 必须产出匹配的平台镜像；不默认套用 x86_64 制品。

Process SDK → Swarm → Core 怎么接

产品内部按 S2 调用边界接入，任务能力按 C3 的单 Agent 思路组织；首版不使用 C5 团队根入口或 X 源码装配。

位置谁提供负责的事情不会自动获得的业务能力
产品调度 / 九问宿主我们认领任务、超时、映射事件、派发 host tool、记录结果故障状态与 CI/发布流程仍需产品实现
Process SDKSwarm 官方Client.run/query、管道、回调、终态/退出码合同不是 HTTP Server，也不持有整个 Case
Process CLI / RuntimeSwarm 官方配置 Agent/模式/Session/权限，装配并执行不自动认识订单、GitHub PR 或恢复标准
DeepAgent / 模型工具循环Core，通过 Swarm 使用真实模型调用、选择工具、读取结果、继续推理模型结论不替代 CI 或业务恢复判据
领域工具我们读日志、源码、修改文件、运行测试、创建 PR提供数据与动作，不返回预置根因或修复补丁

调用及回调合同

入口本设计怎样使用
Client.query("protocol.capabilities")先检查完成状态与所需 feature；发现字段/能力不匹配时停止接入，不靠猜测兼容。
Client.run(...)传任务描述、Agent 定义、workspace、明确工具白名单、host_tools、执行上限与 output_schema。
on_event保存对外可展示的文本、工具过程与身份；按 sequence 去重。chat.final 只表示回答段，不表示执行成功。
on_tool_call仅处理 host_tool.requested，按 call_id/任务身份派发 HTTP 工具；返回真实 JSON 结果或错误。不要把观察性的 chat.tool_call 当作执行命令。
on_interaction展示实际问题/选项并按官方 answers 结构回传同一子进程。自动模式也不一律回答“同意”。未知提问转待人工或停止。
结果 / 取消读取 status、exit_code、output_json、error；SDK 还核对 OS 退出。取消传给仍在持有的 run，不能另起进程取消旧运行。

06

Agent 怎样真正取证与改代码

首版通过 host_tools 接独立领域服务，所有工具必须真实调用；先采用受限工具集合，不依赖 Agent 直接操作 VM 宿主。

工具组 / 建议工具名实际工作执行者与限制
query_metrics / query_logs读取实际指标和日志；返回查询条件、时窗、来源与证据 ID取证服务；单一订单服务，结果有大小限制
get_running_release / get_release_diff取得运行 SHA/digest、配置与变更取证服务读交付账本并与运行实例交叉核对
read_source / list_source从事故版本或候选工作区读取真实源码工程服务；仓库与任务绑定，限制路径
create_workspace / apply_patch / get_diff创建分支工作区、应用模型生成的补丁、返回实际差异工程服务；只改允许业务目录与新增回归测试
run_tests在隔离测试容器中执行固定测试入口工程服务；不把 GitHub 或部署密钥放进候选代码环境
create_pull_request从实际工作区产生提交、推送分支、创建真实 PR工程服务持凭证；返回 PR URL、head SHA，具备幂等键
read_artifact按范围读取大日志、测试输出或 diff取证/工程服务；返回引用和分片，不无限塞进模型上下文
merge / deploy / rollback合并、部署指定 digest、回滚已知正常版仅控制中心身份可调用；不在 Agent 工具白名单中

代码在哪里

源码的完整 checkout 和候选工作区由工程服务管理，测试也在那里隔离执行。Swarm 的 workspace 是独立的 Agent 报告/上下文目录。两者用 case_id 和 workspace_id 关联，首版无需共享一个全权限文件系统。Agent 通过读取和补丁工具实际写代码；工具服务不按故障标签套固定修复。

凭证和执行边界

模型 Key 由九问运行环境读取；GitHub、制品与部署凭证留在工程服务；业务数据库凭证只给业务应用。子进程权限由显式工具白名单和 Runtime 规则收紧，宿主服务再独立校验资源与动作。提示词不能替代工具服务鉴权。

07

一次故障的完整交互时序

点选阶段查看谁做什么。以下内容是执行流程说明，不会调用任何运行系统。

阶段责任交互应留下的事实
01 故障出现观测组件 → 控制中心告警对象、时间窗、运行 release_id；没有预填根因。
02 取证定位控制中心 → 九问 → 取证服务根因假设、证据引用、受影响路径、是否足以修复。
03 生成修复九问 → 工程服务实际 diff、测试记录、候选提交 SHA；代码修复不是预置补丁。
04 创建 PR工程服务 → GitHub真实 PR URL、head SHA、关联 case_id。
05 独立检查GitHub CI → 控制中心可信检查清单、对应 SHA、原始报告；跳过不算本产品通过。
06 合并构建控制中心 → 工程服务 → GitHubmerge SHA → 构建 run → image digest；不部署 latest。
07 部署验证控制中心 → 工程服务 / 九问 / 观测部署回执、运行 SHA/digest、分业务路径的请求与数据库证据。
08 结案或退回控制中心RESOLVED_FIXED 或 RECOVERED_ROLLBACK / NEEDS_HUMAN；后两者不记自动修复成功。

哪些步骤交给模型，哪些交给程序

模型负责决定怎样调查、理解证据、生成修复和解释验证结果。程序负责事件去重、调用授权、CI 检查、合并与部署、指标计算和结案门槛。控制中心不根据“修好了”这句自然语言推进发布。

08

任务、会话和产品状态分别管理

Case 是整件故障，Task 是一次执行尝试，Swarm Session 是框架会话；CI 与发布是另外的长事务。

对象所有者身份与生命周期
Case控制中心case_id：从告警到结案/转人工；浏览器关闭后仍存在
Task / Attempt控制中心 + runnertask_id / attempt_id：调查、修复、验证各自有输入、租约、状态、结果
Swarm Session / RunSwarm；runner 保存映射session_id / request_id：一轮运行与历史；一个 Session 同时只允许运行一条任务
Workspace / Candidate工程服务workspace_id / base_sha / head_sha：实际文件与候选提交
PR / CIGitHub；控制中心对账PR number / 检查 run ID / 检查源码 SHA / 定义版本
Release / Verification工程服务 / 观测验收release_id / merge_sha / image_digest / verification_id
NEW → INVESTIGATING → REPAIRING → PR_OPEN → CI_PENDING → READY_TO_MERGE → MERGED → BUILDING → DEPLOYING → VERIFYING → RESOLVED_FIXED

调查与修复可按两次任务拆分，验证始终是部署后的新任务。它们复用同一套 Agent 能力，不代表多 Agent 团队。后续修复可以按官方合同续接 Session，但必须重发相同 Agent 定义并维持工作区绑定；验证优先新建 Session，显式提供证据清单，避免把旧模型结论当作新事实。

等待 CI/审核/构建时不保留一个空转子进程。控制中心保存状态；阶段完成后启动下一次 run。控制中心重启先查询 GitHub 与交付账本恢复事实，runner 失联不立即重放有副作用工具。

09

PR、CI、合并与发布的版本证据链

每次检查必须对应实际代码，每次发布必须对应实际构建产物。

版本链：拟定的产品合同
事故运行版本 B（source SHA + image digest）
  → 基于 B 的候选分支 C（head SHA）
  → PR 检查（绑定 head 或明确的 test-merge SHA）
  → 控制中心核对基线与 PR 身份，授权合并
  → 实际 merge SHA M
  → 对 M 重新构建并执行业务合同
  → OCI 镜像 digest D（匹配 VM 平台）
  → 部署记录 release_id(M, D)
  → 运行实例报告 M / D
  → 业务验证报告引用同一 release_id
门槛首版规则
候选修改范围业务源码与新增测试可写；可信验收定义、CI 工作流、部署策略、依赖与数据库迁移默认不允许修改
可信 CI由固定工作流/验收定义运行候选；核验检查来源、实际检查 SHA、测试清单和结果。skipped / neutral 不视作本产品的通过
旧结果不能复用PR 新增提交、base 变化或候选变更后重新检查；若 GitHub 检查的是 test-merge SHA，必须记录它与 head/base 的关系
合并权控制中心根据策略决策，交付服务校验并执行；Agent 的 PR 创建身份不能直接合并
合并后变化记录真实 merge SHA；构建和业务合同重新跑在 M 上。候选检查成功不等于新 main 已经验收
制品身份只部署不可变 digest；记录来源仓库、提交、构建 run、架构。部署前确认应用没有被另一事件更新
发布锁单应用串行发布，按期望当前 release_id 做比较；冲突停止并重新取证
回滚保留最近通过业务验证的已知正常版本 A；不能默认回滚到刚才仍有故障的 B

GitHub 官方说明：检查提交与来源；跳过的检查可能不阻止合并。本产品会使用比仓库“可合并”更严格的成功条件。

候选代码与高权限 CI 分开

候选测试环境不注入发布凭证。可信工作流定义来自固定受控版本，不接受 Agent 在候选中修改验收入口。正式选择 GitHub 事件类型与凭证方案时，应核查官方关于不可信 PR 代码执行的约束。GitHub 安全边界说明。

验收：从真实接线到真实恢复

验收是建设后的退出条件。下列数字为拟定测试合同，尚无实测结果。

层次待执行的验收必须保留的证据
G0 环境与版本服务分别健康；仓库可写、模型可用、CI/制品和 VM 平台匹配；能关闭自己的 Web 而后台继续组件清单、镜像/配置哈希、版本基线与连通结果
G1 九问真实接线SDK → CLI → Swarm Runtime → Core → 真实模型 → host tool 全链路；取消/错误/清理至少验证一次run/Session 身份、模型与工具统计、回调记录、终态和 OS 退出
G2 真实故障A 正常；B 下无优惠码订单持续失败，有效优惠码路径仍正常；告警自动创建事件原始请求、指标时窗、异常日志与实际 B 身份
G3 真实修复模型生成实际 diff；可新增回归测试；真实 PR 与正确提交的 CI 成功，禁止靠改验收放行代码 diff、测试明细、PR/CI URL、head/test-merge SHA
G4 真实交付规则满足才合并，M 重新构建/检查；部署的 D 来自 M；运行身份与发布账本一致合并记录、构建 run、digest、部署回执与应用版本
G5 真实业务恢复连续两个60秒观察窗口，每窗口每条正常下单路径至少30次，全部成功且金额正确；无跨路径混算各路径分母、状态码、金额、订单 ID、延迟与窗口起止
G6 数据与语义成功请求对应数据库订单；既有订单仍可读；无效输入保持正确拒绝；候选未关闭故障路径订单持久化核验、旧订单检查、独立合同报告
G7 无人推进与失败边界自动演示路径不需要人逐步下指令；CI失败不发布、未恢复不结案、取消后不再发新动作状态时间线、授权/拒绝原因、动作账本与回滚证据

怎样定义“成功”

只有 G0–G7 的正常修复路径成立，才能把该次记为“自动修复成功”。回滚恢复属于另一类结果。模型结论正确、工具返回成功、CI 通过、容器启动、健康接口返回200，都不能单独代替订单业务恢复。

效果记录

实现后至少做3次干净重置的同类故障运行，完整报告成功与失败，不挑选一条最好轨迹。区分首次发现、提交PR、CI等待、构建发布与恢复验证耗时；记录已报告的 token/费用和未知项，不把未知记为0。该实验只证明这类受控故障的闭环，不推导通用运维成功率。

失败、取消和重启怎样处理

每个阶段都要能停在一个可解释的状态，有副作用的动作先查账再重试。

情况设计处理禁止误判
模型不可用、工具报错、证据不足保留原始错误；有限次数只读重试或 NEEDS_HUMAN不生成预置成功答案
SDK stdout 断流 / 退出码不匹配任务标失败；检查已发生的工具动作；清理持有的子进程不把 EOF 或 chat.final 当成功
超时或调用达到上限记录已执行工具；取消仍在运行的 run；对账后再决定是否新建尝试工具可能已执行，不盲目重复
PR 创建响应丢失按 case_id + 候选 SHA 查询已有分支/PR不创建重复 PR
CI 失败 / head 变了返修次数建议上限2，超过则转人工；新SHA重跑检查不使用旧SHA的绿灯
合并后构建失败保留合并事实，停止部署并标明需修复 main；后续修复走新PR不强推 main 或把已有合并当作未发生
发布失败 / 发布后未恢复回滚到已知正常A，再验证；记录 RECOVERED_ROLLBACK 或 NEEDS_HUMAN不把回滚恢复记成候选修复成功
控制中心或执行服务重启从持久化账本和外部事实恢复；失效租约先对账，确认旧执行终止后再运行不把 SQLite 状态恢复等同 Core Checkpoint 续跑
用户取消停止新任务、请求运行中子进程取消；已合并/已发布的事实不自动撤销取消不是撤销所有外部副作用
重复告警 / 多事件并发告警去重、同应用事件关联、单发布锁不让两个候选同时覆盖同一应用
